How to sequence this against the open PRs

All six Azure PRs report MERGEABLE and all six report REVIEW_REQUIRED. None has merged and none has been reviewed, which is the opening: seven of these findings are code inside #95 and #99 and can be fixed in the PR that introduced them.

First · independent of everything

Ship the Postgres fix as its own PR off main.

Finding 0. One line, already committed and verified, in a file no open PR touches, and it unblocks every external-Postgres deploy on every cloud path. No reason for it to wait behind a six-PR review queue.

Second · before review starts

Push seven fixes back into #95 and #99.

  • #99 introduced aks_required_ips, both service-CIDR checks, and the AGIC and bastion gates. Findings 8, 10, 11, and 13 are all its own code.
  • #95 introduced the resource-group fallback and the attach semantics. Findings 2, 4, 5, and the plan-time half of 3.

Doing it here costs a few extra commits on two unreviewed PRs. Doing it later costs two follow-up PRs against merged code, and reviewers reading the same files twice.

Third · after the stack lands

One wizard follow-up PR.

Findings 1, 9, 12, and 16. This work cannot go on #95: it builds on _load_tfvars from #98, _ask_subnet from #99, and NAME_PREFIX from #96, and #95 never touches quickstart.sh. So it waits for #95, #96, #98, and #99, then arrives as one PR carrying the attach questions, the az aks show lookup, the have-or-create subnet question, and the ClickHouse capacity warning.

Fourth · not urgent, not blocked

Three separate PRs off main.

Findings 6, 14, and 15 are all pre-existing on main and touch files none of the six PRs touch, so they can run in parallel with everything above, in any order. Check PR #100 before opening the one for finding 15, since it overlaps that work on the enable_* flags.

Verified by running: the fixture applies; make preflight passes every check; terraform plan and terraform apply both succeed on the attach path and the state converges to "No changes"; the customer's cluster, VNet, and subnet appear in state only as data. reads, with zero managed cluster, VNet, subnet, or node pool resources; nine of ten negative tests reject a bad config at plan time. Finding 8 was hit as a live failure rather than derived from reading, and finding 12's numbers were read off live nodes.

Caveats: Redis ran in-cluster because Azure Managed Redis could not allocate in eastus2 at either SKU, so the managed-Redis path is covered by plan-time checks only. The license key was a placeholder, so the LangSmith chart itself was never installed. Findings 10, 13, 14, and 15 were confirmed by tracing every consumer across the module rather than by a failing apply. Whether Terraform preserves explicit newlines in error_message is unverified, and it shapes finding 11's fix.
